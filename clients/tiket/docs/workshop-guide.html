05 — Concepts

The Eight Building Blocks

Cowork gives you chat and projects. Claude Code gives you a real configuration system. These are the eight primitives you compose to build enterprise-grade agentic workflows — each solves a problem Cowork can't.

MCP (Model Context Protocol)

Universal connectors that let Claude talk to external tools — APIs, databases, SaaS products. Think USB ports for AI.

// .mcp.json { "mcpServers": { "google-sheets": { "command": "npx", "args": ["@anthropic/sheets-mcp"] } } }
USB ports for your AI — plug in any tool

Skills

Reusable instruction sets that teach Claude how to do specific tasks — like SOPs for your AI assistant. Triggered with /skill-name.

# ~/.claude/skills/write-blog.md # Blog Writer Skill ## Steps 1. Read brand voice from CLAUDE.md 2. Research topic using web search 3. Write draft following template 4. Apply SEO best practices
A recipe book — each skill is a step-by-step recipe

CLAUDE.md

A configuration file that tells Claude who it is, what standards to follow, and how to behave. Lives at the root of your project.

# CLAUDE.md # Brand Voice - Tone: professional, warm - Audience: B2B travel executives - Never use: "revolutionary", "synergy" - Always include: data + proof points
An employee handbook — standards everyone follows

MEMORY.md

Persistent memory across sessions. Claude remembers past decisions, learnings, and context so it doesn't start from scratch every time.

# MEMORY.md ## Learnings - Blog posts > 2000 words rank better - VP prefers bullet-point summaries - Campaign naming: YYYYMM-channel-topic ## Decisions - Approved: new content calendar format - Rejected: automated social posting
A journal — it remembers so you don't have to repeat yourself

Agents (Sub-Agents)

Specialized co-workers with their own role, tools, and model. Delegate to them when a task needs focus or cheaper compute — your main agent calls them like Slack handoffs.

# .claude/agents/feedback-editor.md --- name: feedback-editor description: Turn scattered review comments into clean rewrites. tools: Read, Grep, Edit, Write model: haiku --- You are a senior editor. Read the original doc and all reviewer comments, understand the intent behind each, and rewrite cleanly — don't just append "addressed" notes.
A specialist consultant — called in only when you need them, paid only when used

Commands

Slash-commands you invoke by name — /explain-change, /partner-report. Turns repetitive workflows into one-liners the whole team can call.

# .claude/commands/explain-change.md --- description: Explain a recent code/content change argument-hint: [file path] --- Read $ARGUMENTS (or the most recent change) and produce: 1. What was changed 2. Scope of impact (files / modules / features) 3. Refactor vs. behavior change 4. What to test first
A tool in your toolbar — always one click away

Hooks

Event triggers that run *automatically* before or after Claude does something. Use them to enforce checks you don't want to rely on Claude to remember.

# settings.json { "hooks": { "PreToolUse": [{ "matcher": "Bash(git commit *)", "hooks": [{ "type": "command", "command": ".claude/hooks/lint-check.sh" }] }] } }
A tripwire — invisible until it catches something

Rules (with paths:)

Domain-specific guardrails that only load when Claude touches matching files. Split brand voice, API conventions, and tone rules into separate files that activate contextually — keeps context clean.

# .claude/rules/blog-voice.md --- paths: - "content/blog/**/*.md" --- # Blog Voice Rules - Tone: warm, concrete, specific - Never use: "revolutionary", "synergy", "unlock" - Open with a question or a scene, not a claim - Every post needs one data point + one story
Context-aware seatbelts — they only click in when you're in the right seat

Deep dive: Agents — the three kinds

The default way most people use Claude Code is "one AI does everything." That works — until it doesn't. Agents let you set up different specialists, each with their own role, tools, and behavior rules. When Claude hits a task that matches one, it hands off to the specialist — the way a manager assigns work to the right team member instead of doing it all themselves.

Type 1 — Built-in

Pre-built sub-agents

Claude Code ships with a few generalists: Explore, Plan, general-purpose. Claude decides when to call them automatically. Their job: common utility work like codebase exploration and planning — the stuff every project needs.

When you benefit: automatically — you don't have to configure anything.

Type 2 — Custom

Your own sub-agents

Live in .claude/agents/. These are specialists you design for your workflow — a feedback editor, a partner researcher, a brief writer. Each has its own role, its own allowed tools, and its own model (cheap models for cheap work).

When you benefit: when a task recurs often enough that you'd rather delegate than re-explain every time.

Type 3 — Cloud

Managed Agents (Anthropic-hosted)

Anthropic's recently-released hosted agent infrastructure. You define the agent's tools, MCP servers, and model; Anthropic spins up a cloud container and runs it for you, for minutes or hours, with no laptop involved.

When you benefit: when the work needs to happen without a human driver — overnight, scheduled, or triggered by external events.

How sub-agents get triggered

There are three ways a custom agent gets called in the middle of a conversation:

  1. Auto-triggered. Claude reads the agent's description field and decides on its own whether the current task matches. This is why a crisp, specific description is the most important thing you write. Vague descriptions = ignored agent.
  2. Directly specified. You say "please use the feedback-editor agent to clean up this doc." Claude hands off explicitly.
  3. @-mentioned. You type @"feedback-editor (agent)" in the chat. Manual, explicit, and visible in the transcript.

Rule of thumb: design for auto-trigger. If you're always having to manually invoke an agent, your description isn't doing its job.

Sample custom agent

A real, copyable example — a feedback editor that a content team could use to process scattered review notes into clean rewrites.

.claude/agents/feedback-editor.md
--- name: feedback-editor description: Use when turning scattered review comments, editor notes, or slack threads into a cleanly rewritten draft. tools: Read, Grep, Edit, Write model: haiku --- You are a senior content editor. When given an original document plus a set of review comments or scattered feedback: 1. Read the original content carefully 2. Read ALL the feedback first before touching anything 3. Understand the intent behind each comment — not just the literal text. What is the reviewer *actually* worried about? 4. Rewrite the document cleanly. Do not append "addressed" notes or leave tracked-change artefacts. 5. Preserve voice and structure where possible. 6. Flag any feedback you chose NOT to apply, and explain why. You are allowed to disagree with a reviewer if their suggestion conflicts with something deeper in the document. Surface the conflict, don't silently pick a side.

Notice: model: haiku because this is mostly rewriting work, not deep reasoning. Notice: tools: is minimal — the editor doesn't need shell access, doesn't need to run scripts, doesn't need the internet. Fewer tools = safer, cheaper, more predictable.

06 — Architecture

Team Architecture

The difference between Cowork and Code isn't just features — it's governance. Here's how each structures team instructions.

Cowork

Flat 2-Layer Structure

Each person has their own Projects. No shared layer. No inheritance. No central control.

Person A — their projects
Person B — their projects
Person C — their projects

No connection between team members.

Code

Multi-Layer with Inheritance

Layered system where org standards flow down to every team member automatically via Git.

Organization CLAUDE.md
↓
Project CLAUDE.md
↓
Personal .claude/ overrides

Standards cascade. Everyone stays aligned.

Governance Gaps in Cowork

No Version Control

Instructions change without history. No way to audit what changed or roll back mistakes.

No Shared Standards

Each person configures Claude differently. Brand voice, tone, and quality vary across team.

No Permission Layers

No distinction between org-level rules and personal preferences. Everything is flat.

No Audit Trail

VPs and managers can't review what instructions agents are following or verify compliance.

What's actually inside .claude/

The cascade above shows how instructions flow. This is what each layer contains. Every primitive from Section 05 lives in this folder tree — committed to git, shared across the team.

# Personal (applies across all your projects) ~/.claude/ ├── CLAUDE.md # your personal defaults └── settings.json # permissions, hooks, env # Project (committed to git — the whole team gets it) ./.claude/ ├── CLAUDE.md # project overview, stack, conventions ├── settings.json # shared permissions + hooks ├── settings.local.json # personal overrides (gitignored) │ ├── agents/ # specialized sub-agents │ ├── feedback-editor.md │ ├── partner-researcher.md │ └── brief-writer.md │ ├── commands/ # slash-commands │ ├── explain-change.md │ ├── partner-report.md │ └── weekly-recap.md │ ├── hooks/ # event-triggered shell scripts │ ├── before-commit-check.sh │ └── after-write-format.sh │ ├── rules/ # domain rules (lazy-loaded by paths:) │ ├── blog-voice.md # loads only for content/blog/** │ ├── api-conventions.md # loads only for src/api/** │ └── outreach-tone.md # loads only for outreach/** │ └── skills/ # reusable work manuals ├── partner-report/ │ └── SKILL.md └── weekly-deck/ ├── SKILL.md └── templates/
Agents vs Commands vs Skills

Agents = specialists you delegate to. Commands = keyboard shortcuts for repeated workflows. Skills = detailed work manuals Claude auto-loads when relevant.

Hooks vs Rules

Hooks are enforced by your system (shell scripts, always run). Rules are loaded into Claude's context (guidance, not enforcement).

CLAUDE.md vs Rules

CLAUDE.md is the always-loaded project brief — keep it concise. Rules are heavy, domain-specific details that only load when Claude touches matching files.

Getting Started with Claude Code

Six steps from zero to your first team workflow. Follow along — this is the hands-on part.

1

Press Cmd+Space, type "Terminal", hit Enter. This is your command center.

$ # Cmd+Space → "Terminal" → Enter
2

Navigate to Your Project Folder

Use cd to move into the directory where your project lives. This is where Claude will operate.

$ cd ~/my-project
3

Launch Claude Code

Type claude and press Enter. Claude boots up and reads your project context automatically.

$ claude ╭──────────────────────────────────╮ │ Claude Code v1.x │ │ Reading project context... │ │ Ready. │ ╰──────────────────────────────────╯
4

Create Your CLAUDE.md

Define your team's brand voice, quality standards, and guardrails. This file is the foundation of everything.

$ cat > CLAUDE.md << 'EOF' # Team Standards ## Brand Voice - Professional, data-driven, warm - Audience: B2B travel executives - Language: English & Bahasa Indonesia ## Quality Gates - All content reviewed before publishing - Include data sources for claims EOF
5

Build Your First Skill

Create a reusable skill file. This teaches Claude a repeatable workflow your team uses often.

$ mkdir -p .claude/skills $ cat > .claude/skills/weekly-report.md << 'EOF' # Weekly Report Skill ## Goal Generate a weekly marketing performance summary. ## Steps 1. 6

Share with Your Team

Commit and push. Now every team member who pulls the repo gets the same standards and skills.

$ git add CLAUDE.md .claude/ $ git commit -m "Add team standards and first skill" $ git push origin main
08 — Skills

Building Great Skills

Skills are the building blocks of team AI. A well-written skill turns a vague request into consistent, high-quality output every time.

Anatomy of a Skill File

# skill-name.md ## Goal One sentence: what this skill produces. ## Context Who uses this, when, and why. ## Inputs - What the user provides (topic, data, brief) - What Claude reads from context (CLAUDE.md, files) ## Steps 1. First, do this... 2. Then, do this... 3. Finally, produce this output. ## Output Format Describe the expected deliverable format. ## Quality Checks - [ ] Matches brand voice - [ ] Includes data citations - [ ] Under 500 words

Be Specific

Write clear, concrete instructions. "Write a 300-word summary" beats "write a summary." Specificity reduces variance.

Include Examples

Show Claude what "good" looks like. Include sample outputs, tone examples, or reference docs. One example is worth a hundred instructions.

Iterate Relentlessly

Run the skill, review the output, fix the instructions. Good skills take 3-5 iterations to get right. Don't stop at version one.

09 — Advanced

Advanced Features

Once you're comfortable with the basics, these features let you build truly powerful agent systems.

Model Routing

Pick the right model for each task. Haiku for quick drafts and lookups, Sonnet for daily work, Opus for complex multi-step pipelines. Use /model to switch mid-session. Optimize cost and speed without leaving the conversation.

Context Management

Use /context to check token usage and /compact with custom instructions to surgically compress at logical breakpoints. System prompts, tools, and MCP schemas consume 30–40K tokens before you type anything — performance degrades around 147K, not 200K. Compact after finishing a feature or resolving a bug, not mid-task. The 1M context window (Opus 4.6 / Sonnet 4.6) gives 5× headroom with no pricing premium on Max/Team/Enterprise.

Plan Mode

Ask Claude to plan before executing. Review and approve the plan, then let it run. More control for high-stakes tasks.

Hooks

Run scripts before or after Claude actions. Enforce code formatting, linting, or custom validation automatically.

MCP Plugins

Install pre-built connectors from the community. Google Sheets, HubSpot, Airtable, Slack — hundreds available and growing.

Skill Creator

Use /skill-creator to generate new skills interactively. Describe what you need and Claude builds the skill file for you.

Subagents

Spawn child agents for parallel tasks. One agent researches while another writes. Divide and conquer complex workflows.

Agent Teams

Define named agents with specific roles — writer, researcher, analyst, reviewer. Orchestrate them from a lead agent.

Git Worktrees

Work on multiple branches simultaneously without stashing or switching. Each worktree is a separate folder with its own branch — like having multiple desks for the same project.

Evals

Measure how well your skills and prompts actually perform. Run automated test cases, compare outputs across iterations, and catch regressions before they reach your team.

Headless Mode

Run Claude non-interactively with claude -p. Pipe prompts in, get results out. Embed in cron jobs, shell scripts, or CI pipelines — automate recurring reports and workflows without human babysitting.

Managed Agents

Anthropic’s hosted agent infrastructure. Define an agent (model, tools, MCP servers), spin up a cloud container, and let Claude run autonomously for minutes or hours — no custom loop or sandbox needed.

10 — Hooks

Event-Driven Automation

Hooks run outside of Claude. They're shell scripts your system executes before or after tool calls — the place to put checks you refuse to rely on Claude to remember. If it must happen every time, it's a hook, not an instruction.

Why hooks, not prompts

You can write "always run lint before committing" in CLAUDE.md. Claude will forget. You can write it in a skill. Skills don't always load. A hook is the only place that guarantees execution — because your shell runs it, not the model.

Rule of thumb: if skipping the step would break production, make it a hook.

Common event types

  • PreToolUse — before Claude runs a tool (intercept, validate, block)
  • PostToolUse — after a tool succeeds (format, test, log)
  • SubagentStart / SubagentStop — when sub-agents spin up or finish
  • FileChanged — when a watched file is modified
  • Stop — when Claude finishes a turn (notify, summarize)

Real example: lint-before-commit

Before Claude is allowed to run git commit, your system runs a lint check. If lint fails, the commit is blocked — Claude sees the error and fixes it.

.claude/hooks/before-commit-check.sh
#!/usr/bin/env bash set -euo pipefail echo "Running lint and format..." npm run lint npm run format -- --check
.claude/settings.json
{ "hooks": { "PreToolUse": [{ "matcher": "Bash(git commit *)", "hooks": [{ "type": "command", "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/before-commit-check.sh" }] }] } }

The matcher is a glob on tool invocations. $CLAUDE_PROJECT_DIR lets the same hook work across team members.

Marketing / content examples

  • PostToolUse on Write(*.md) → run a readability checker, reject if grade level too high
  • PreToolUse on Bash(hubspot *) → confirm the contact list size before a bulk send
  • Stop hook → ping Slack with a 1-line summary of what Claude just did
  • PreToolUse on Bash(rm *) → auto-deny destructive commands entirely
11 — Rules

Lazy-Loaded Guardrails

Rules solve a problem you'll hit fast: you can't put everything in CLAUDE.md or Claude drowns in context. Rules let you split guardrails by domain and load them only when Claude touches matching files — brand voice for blog posts, tone rules for outreach, API conventions for backend work.

The paths: frontmatter pattern

Every rules file has optional frontmatter that declares which files it applies to. No match → not loaded → no token cost.

.claude/rules/blog-voice.md
--- paths: - "content/blog/**/*.md" --- # Blog Voice ## Tone - Warm, concrete, specific - Written like a senior operator talking to a peer ## Never use - "revolutionary", "synergy", "unlock", "seamless" - Opening with a claim (open with a scene or question) ## Always include - One data point with source - One first-person story or example
.claude/rules/outreach-tone.md
--- paths: - "outreach/**/*.md" - "outreach/**/*.txt" --- # Outreach Tone ## Subject lines - Max 7 words - No emoji, no "Quick question" ## Opening - First line must reference something specific from the prospect's last 30 days - Never "Hope this finds you well" ## CTA - Always optional ("No reply needed if not a fit") - Single ask, never two

Rules vs CLAUDE.md vs Skills

Use When Loads
CLAUDE.md Always-true project facts — stack, conventions, key commands Every conversation
Rules Domain guardrails — brand voice, API patterns, tone by channel Only when matching files are touched
Skills Multi-step procedures — "how to produce a weekly partner report" When user invokes or task matches
12 — Permissions

settings.json & Allow/Deny Lists

The permissions system is what makes Claude Code safe to deploy on a real team. You declare exactly which tools Claude can use, which commands it can run, and which are forbidden — committed to git, enforced by the harness.

Three places settings.json lives

PERSONAL
~/.claude/settings.json

Your defaults across every project. Never committed.

TEAM (SHARED)
./.claude/settings.json

Committed to git. Everyone on the team inherits these rules.

LOCAL OVERRIDES
./.claude/settings.local.json

Your personal overrides for this project. Gitignored.

Real example: a marketing team's shared settings.json

{ "permissions": { "allow": [ "Read", "Edit", "Write", "WebFetch", "WebSearch", // Sheets & Docs for reports "Bash(gws sheets *)", "Bash(gws docs *)", // Git for version-controlled content "Bash(git status)", "Bash(git diff *)", "Bash(git log *)", "Bash(git add *)", "Bash(git commit *)" ], "deny": [ // Never let an agent wipe a repo "Bash(rm -rf *)", "Bash(git push --force *)", // No bulk sends without human "Bash(gws gmail +send *)", "Bash(hubspot:send-bulk *)", // No piping untrusted scripts "Bash(curl * | sh)", "Bash(curl * | bash)" ] } }

Deny always wins over allow. Any tool not listed in allow triggers an interactive prompt — the user gets asked before Claude acts.

Why this matters for non-technical teams

Cowork gives everyone the same blank permissions. Claude Code lets you build a safety envelope your team agrees to once, then works inside forever. Sales can use the CRM but not bulk-send. Content can push to staging but not production. Everyone has git read but not force-push. It's the first real answer to "how do we let marketing use AI agents without giving them nuclear launch codes."

13 — Philosophy

The Mindset Shift

Using Claude Code well isn't about prompting tricks. It's about thinking differently about how you work with AI.

01

Goals, Not Steps

Tell Claude what you want to achieve, not how to do it. "Increase blog traffic 20%" beats "Write 5 blog posts about X." Let the agent figure out the path.

02

Chain, Don't Repeat

Build on previous outputs. Use skills that reference other skills. Create pipelines where one step feeds the next, instead of starting from scratch each time.

03

Document Your Workflows

If you do something twice, write a skill. If the skill works, share it with the team. The best teams turn tacit knowledge into reusable instructions.

04

Collect References

Feed Claude examples of great work — competitor campaigns, top-performing content, style guides. The more context it has, the better the output.

05

Iterate Relentlessly

Version one is never the final version. Review outputs, refine instructions, test again. The teams that iterate fastest win — and AI makes iteration nearly free.
