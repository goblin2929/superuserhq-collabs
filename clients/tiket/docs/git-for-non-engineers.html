Coordination Primer

Git is the New Notion

If you can use Notion, ClickUp, or Trello, you can use git. This is a plain-English guide for non-engineers — because git is the shared workspace where humans and agents coordinate without stepping on each other.

01

Why non-engineers need git

Engineers have used git for 20 years to coordinate with each other. It turns out, those same tools are exactly what you need to coordinate with agents. Not a coincidence — agents work the same way a distributed team of humans does.

The coordination problem

You and an agent (or two agents, or a teammate plus an agent) are both editing the same document. Who's version is right? How do you merge changes? What if the agent overwrites your edit? What if you overwrite the agent's?

Notion and ClickUp give up on this problem — they just use "last write wins" and cross fingers. Git actually solves it.

Git's answer

Every change is tracked. Every version is recoverable. Parallel changes merge cleanly. Conflicts are surfaced, not silently lost. And — this is the part non-engineers miss — the whole system is designed for people who are not in the same room, not in the same timezone, and not doing the same thing at the same time.

Which is exactly your relationship with an agent.

If you've ever said "did you save the latest version?" at work, you already know why git exists.
02

The Notion/ClickUp/Trello Translation

Every git concept has a direct analog in tools you already use. Here's the full map.

Git concept If you're used to… What it actually does
Repo Notion workspace / ClickUp space The whole project. A single folder everyone shares.
File Notion page / ClickUp doc An individual document. Lives inside the repo.
Commit "Save version" in Google Docs A snapshot of a change, with a message describing what and why. Permanent, searchable, revertable.
Branch A duplicated page you're drafting on A parallel line of work that doesn't affect the main version until you merge it in.
Main branch The "published" page in Notion The version everyone treats as the source of truth. Only tested, reviewed work lands here.
git pull Hitting refresh in Google Docs Download everyone else's latest changes into your copy.
git push "Share page" / "Publish" Upload your committed changes so the rest of the team can pull them.
Worktree Opening a second tab of the same page to compare A second physical folder on your machine pointing at a different branch of the same repo. Lets you work on two things without swapping.
Merge Accepting tracked changes in Word Combining two branches into one. If there are conflicts, git asks you which version wins, line by line.
Conflict Two people editing the same Notion block Two branches changed the same line differently. Git pauses and asks you to pick — never silently loses your work.
Revert Google Docs "version history → restore" Undo a past change cleanly, without losing everything that came after it.
03

The Five Moves You Actually Need

95% of git, for a non-engineer, is five commands. Learn these and stop.

1. git pull

When: at the start of any working session.

$ git pull

Downloads whatever your teammates (human or agent) pushed since you last looked. Always do this first. Always.

Same as hitting refresh before you start editing a shared Google Doc

2. git status

When: any time you want to see what's changed.

$ git status

Shows you which files are modified, which are new, which are ready to be committed. Your "what have I done since I last saved?" view.

Same as looking at the "edited" markers next to pages in Notion

3. git add + git commit

When: you finished a unit of work and want to save it.

$ git add partner-report.md $ git commit -m "Draft Q2 Marriott partner report"

The commit message is the why. Write it like you're texting a future teammate who's asking "what did you do and why?" Future you will thank you.

Same as naming a version in Google Docs history so you can find it later

4. git push

When: you want your teammates (or an agent) to see your work.

$ git push

Uploads your committed work to the shared repo. Until you push, your work only exists on your laptop.

Same as "share" or "publish" in Notion. Before this, you're drafting.

5. git log

When: you want to know what happened, by whom, and when.

$ git log --oneline -20

Shows the last 20 changes in the repo with one-line messages. This is your audit trail — who touched what, when, and why. VPs love this. Compliance loves this. Your future self loves this.

Same as Notion's activity feed — but trustworthy, forever, and includes agents
04

The Main Branch is the Version of Truth

If you take one concept away from this page, take this one. Everything else follows from it.

The rule

The main branch is the version of the project that your team treats as real. It's the "published" copy. It's the one the dashboard shows, the one the client sees, the one a new teammate would pull. Nothing broken, nothing half-finished, nothing experimental lives on main.

Why this matters with agents

Agents will cheerfully write 500 lines of content, commit it, and push it — if you let them. Without a main-branch discipline, you will wake up one morning to find the "published" version of your partner reports is whatever an agent did at 3am. With discipline, the agent works on a branch, you review, and you decide when it lands on main.

The loop

main │ ├── agent-q2-partner-research # agent does its work here │ ↓ │ (review by you) │ ↓ │ merge into main # only after you approve │ └── your-draft-q2-recap # you draft here ↓ (test, polish) ↓ merge into main # only when it's ready to be real

Main is the airlock. Branches are where work happens. Merges are the decision points where you are in charge.

If main always works, you can always ship. That's the whole game.
05

Worktrees: Parallel Desks for Parallel Work

Worktrees are git's best-kept secret for non-engineers. They let you work on two things at once without swapping contexts.

The problem they solve

You're mid-draft on a partner report. A colleague pings: "can you urgently edit the Q1 deck?" Normally you'd stash your partner report work, switch branches, lose your place, come back confused.

Worktrees solve this: you open a second folder for the Q1 deck branch, edit it, commit, go back to your partner report folder. Both folders exist on disk at the same time. No context loss.

How you use them

# from your main project folder $ git worktree add ../tiket-q1-deck q1-deck-branch # now you have two folders: # ~/projects/tiket/ (main work) # ~/projects/tiket-q1-deck/ (urgent edit) # work in either. commit in either. switch freely.

Why worktrees are perfect for agent coordination

Here's the real unlock: you can have a long-running agent working in one worktree while you work in another.

Desk 1: You

Writing a Q2 partner recap. Your main workspace, main branch.

Desk 2: Agent A

Researching Marriott's 2026 growth announcements in a separate worktree on research-marriott. Takes 20 min.

Desk 3: Agent B

Drafting three cold outreach variants in a separate worktree on outreach-drafts. Takes 5 min.

Three desks, three jobs, zero stepping on each other. When an agent finishes, you review its desk, merge (or don't), and move on. Your main work never gets interrupted.

A worktree is a second monitor for your project — same project, different screen, different work
06

Working Alongside Agents

Once you have git, you have everything you need to coordinate with an agent the way an engineering team coordinates with each other.

The four-step cycle

  1. Brief on a branch. Create a new branch for the task. Tell the agent "work on partner-recap-q2". The agent stays out of main by design.
  2. Let it run. The agent does its work, commits as it goes (commit messages become your audit trail of what it did). You do other things — maybe in a worktree.
  3. Review before merge. Pull the agent's branch. Read the diff. Check what it touched. Ask questions. This is the step most people skip — don't.
  4. Merge or discard. If you like it, merge into main — now it's "real." If not, drop the branch. Nothing was ever at risk. The main version was never touched.

Real example: a Tuesday morning

# 9:00am — start your day $ cd ~/projects/tiket $ git pull # sync whatever happened overnight # 9:05am — brief an agent to research a partner in a worktree $ git worktree add ../tiket-research research-hilton $ claude # open Claude Code in the research worktree > /partner-research Hilton Jakarta # kick it off # 9:15am — work on your main thing while the agent runs $ cd ~/projects/tiket $ claude > Help me outline the Q2 review deck # 10:30am — check on the agent $ cd ~/projects/tiket-research $ git log --oneline -5 # see what it did $ git diff main..research-hilton # read the changes # if good, merge; if not, drop $ cd ~/projects/tiket $ git merge research-hilton # land the agent's work $ git push # publish to the team

That's a full human+agent coordination loop. The entire trick is: agents work on branches, you review diffs, you own the merge. Nothing else to learn.

07

The Three Fears Non-Engineers Have About Git

And why each one is overblown once you understand how git actually works.

"I'll delete something important"

You can't. Git is essentially impossible to permanently break through normal use. Every commit is saved, reflog tracks even discarded work for 90 days, and any "destructive" command has a recovery path.

The only genuine ways to lose work are rm -rf (not a git command) and git push --force — and both are easy to put behind a permissions deny-list.

"It's too technical"

Five commands: pull, status, add, commit, push. That's it for 95% of workflows. Everything else is a special case you learn once, ten times a year.

You learned Cowork. You learned Notion. You learned ClickUp. Git is smaller than any of those — it just looks intimidating because engineers hoard it.

"What if there's a conflict?"

Conflicts are features. They mean git caught two people (or an agent and you) editing the same thing differently — and is asking you to choose instead of silently losing one version.

Notion and Google Docs don't have conflicts. They just overwrite. Ask yourself which you'd rather.

If you can use Notion, you can use git. The only difference is git is honest about when it needs you.
