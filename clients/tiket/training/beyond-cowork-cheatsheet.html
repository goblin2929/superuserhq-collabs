07When to write a skill

Second time you explain the same thing to Claude — that’s a skill waiting to be written.

  • Re-describing your PR-feedback structure
  • Re-pasting your brand voice rules
  • Re-explaining your audit methodology

Write it once. Description = the trigger. Body = your standard. Every matching session gets it free.

08Anatomy of a skill
~/.claude/skills/prospect-audit/
├── SKILL.md      # required · the manual
├── references/   # rules · on demand
├── scripts/      # fetch · checks
└── assets/       # templates

On-demand loading: the description is always indexed; folders load only when the task needs them.

description is the trigger — Claude matches your prompt against it.

10What makes a good skill
  • Sharp description — names the trigger, not “affiliate tool”
  • One job — one skill = one procedure
  • Names its inputs — “requires GA4 ID, month”
  • Short body — push detail to references/
  • Earns its place — written from a real repeat

13Context window & rot

One shared working memory per session (1M ceiling). Bigger isn’t better — accuracy drops as it fills.

Signs of rot: forgets early instructions · output goes generic · inconsistent across runs · drops plan steps.

Fixes: trim CLAUDE.md · split procedures into skills · delegate to agents (fresh ctx) · /clear & reset.

14Hooks · gates · the learning loop
  • Hook — a tripwire your computer runs (not Claude): before risky moves, after every edit, when Claude stops.
  • Gate — a hook that blocks/flags work that fails a check.
  • Learns without retraining — a stop-hook writes one line to MEMORY.md; next session reads it back.
15The safety envelope

Three concentric layers. No surprises.

  • Permissions — what Claude can’t do. Hard block.
  • Hooks — what the system enforces. Tripwire.
  • Instructions — what Claude should do. CLAUDE.md + skills.

All version-controlled. All auditable.
